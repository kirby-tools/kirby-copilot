# Agents Prepare, Editors Publish

An agent edits site content from outside the Panel, acting as the Kirby user who connected it. With Prepare changes, its writes stop short of published content: field changes become the model's unsaved changes, which an editor reviews, publishes, or discards in the Panel; a new page starts as a draft, and a file uploaded into a draft waits with it. Ending a review or going live at once – publishing or discarding unsaved changes, changing a page's status, slug, or parent, uploading outside a draft – takes the Publish changes connection permission, and deleting takes Delete content. Both are off when a user connects an agent, granted only by ticking them, and capped by the user's Kirby role.

The line runs between what waits for review and what doesn't. An agent is untrusted – its instructions may come from content it read or from a prompt nobody in the Panel wrote – so its output needs a review gate before it goes live. Kirby has exactly one for content: a model has published content and unsaved changes and nothing else (`Content/VersionId.php`). A draft is the same gate for a whole page: nothing in it is published content until someone changes its status.

Content Translator rejected writes to unsaved changes for its cascades (its ADR `0001-cascade-writes-latest.md`) because of the editing lock and the per-language publish. Both hold in Kirby 5.6 and 6, and here they are the price of the gate.

## Consequences

- After an agent write, the model carries the connected user's lock for ten minutes, or until its unsaved changes are published or discarded, so colleagues see it as edited by that user.
- Publishing is per model and per language: an agent that prepares N models in M languages leaves N × M publishes, in the Panel or as per-language `publish_changes` calls with Publish changes. A tool call writes one model, and nothing promises "translate the whole site".
- A Panel tab opened before the agent wrote sends its whole in-memory form back on every keystroke, on publish, and on leaving the view (`panel/src/panel/content.js`), overwriting the agent's write. Kirby's lock can't catch this, because the agent writes as the same user. A view that is open while an agent writes reloads within ten seconds while its tab is visible, or when the tab regains focus; an edit in that window still overwrites the agent's write. Agent writes aren't refused while the user edits in the Panel: that would block the common case of an editor asking an agent to rework the page they have open, to guard a window of seconds.
- A write that brings in active markup the field doesn't already hold – a script-like element, an event attribute, or a script URL in markup or as the whole value of a `url` or `link` field, nested ones included – is refused, since the Panel's preview would run it on the Panel's origin and templates print such values into `href`. It is a denylist on new content rather than an HTML allowlist, so an editor's embeds survive a rewrite. Below PHP 8.4, it parses with libxml, which before 2.14 reads some markup unlike a browser, so active markup can slip through there.
- Kirby keeps unsaved changes for a file's fields, not for the file itself, so an upload is live at once wherever published content can reach it. In a draft, or a page inside one, it waits with the page: like the draft's own preview, its media URL carries a token nothing published links to, and the file goes live when the draft does.
- A new slug or parent changes a published page's URL at once, outside the review that unsaved changes give, so changing a slug or moving a page takes Publish changes like a status change – on a draft too, so `change_slug` and `move_page` need one permission whatever page they act on.
- Publishing and discarding take a model's unsaved changes in a language as a whole, the user's own Panel edits included, as the Panel's buttons do. They aren't limited to the changes an agent prepared: an agent could claim any changes by resending a field unchanged, and the user who grants publishing asks for exactly that.
- A role blueprint withholds publishing or deletion from agents with the plugin permissions `agentsPublish` and `agentsDelete`, even where the role may publish or delete in the Panel. The cap applies to existing connections on their next request.
- Any of Kirby's content actions for pages, files, and the site may become a tool, behind this gate. Left out for good are what Kirby itself lacks, such as scheduled publishing and revisions; administration, such as users, roles, and languages; and taking over a colleague's lock.
