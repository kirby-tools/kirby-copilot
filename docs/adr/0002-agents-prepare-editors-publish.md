# Agents Write to `changes`, and Publishing Is a Permission of Its Own

An agent edits site content from outside the Panel, acting as the Kirby user who connected it. Its field changes to existing content become the model's unsaved changes – Kirby's `changes` version, which an editor reviews, publishes, or discards in the Panel – and a new page starts as a draft. Publishing and deletion are connection permissions of their own: off when a user connects an agent, granted only by ticking them, and capped by the user's Kirby role. Publishing covers publishing and discarding unsaved changes, and the changes that are live at once, such as a page's status, slug, or parent.

Content Translator rejected writes to `changes` for its cascades (its ADR `0001-cascade-writes-latest.md`): every write stamps the editing user's lock, and `Version::publish()` publishes one language. Both facts still hold, in Kirby 5.6 and 6. What is new is the author. An agent is untrusted – its instructions may come from content it read or from a prompt nobody in the Panel wrote – and its output needs a review gate before it goes live. Kirby has exactly one: a model has a `latest` and a `changes` version and nothing else (`Content/VersionId.php`). The lock and the per-language publish are the price of that gate.

## Consequences

- Every model that holds an agent's field changes carries the connected user's lock until it expires, so colleagues see it as edited by that user. The user isn't locked out, since Kirby exempts the lock's own holder (`Content/Lock.php`).
- Publishing is per model and per language: an agent that prepares N models in M languages leaves N × M publishes, in the Panel or as explicit per-language calls with the publish permission. A tool call writes one model, the docs steer toward single-page jobs, and nothing promises "translate the whole site".
- A Panel tab opened before the agent wrote sends its whole in-memory form back on every keystroke, on publish, and on leaving the view (`panel/src/panel/content.js`), overwriting the agent's field changes. Kirby's lock can't catch this, because the agent writes as the same user. A view that is open while an agent writes reloads within ten seconds while its tab is visible, or when the tab regains focus; an edit in that window still overwrites the agent's changes. Agent writes aren't refused while the user edits in the Panel: that would block the common case of an editor asking an agent to rework the page they have open, to guard a window of seconds.
- A field change that brings in active markup the current value doesn't hold – a script-like element, an event attribute, a script URL – is refused, since the compare preview would run it on the Panel's origin. It is a denylist on new content rather than an HTML allowlist, so an editor's embeds survive a rewrite. Below PHP 8.4, which brings an HTML5 parser, libxml parses the value and reads some markup differently from a browser; the elements where it is known to (`noscript`, `svg`, `math`, `template`) count as a whole on every PHP version, and a differential outside them would pass. libxml before 2.14 parses HTML4, so with it a value that holds a comment, an element whose content is text, or a reference to no character XML allows is refused outright.
- A new slug or parent changes the page's URL at once, outside the review that unsaved changes give, so changing a slug or moving a page takes the publish permission, like a status change.
- Publishing and discarding take a model's unsaved changes in a language as a whole, the user's own Panel edits included, as the Panel's buttons do; Kirby refuses while another user's lock is active. They aren't limited to the changes an agent prepared: an agent could claim any changes by resending a field unchanged, and the user who grants publishing asks for exactly that.
- Uploaded files are live at once: Kirby keeps unsaved changes for a file's fields, not for the file itself, so only those fields wait for review, and uploading needs the publish permission.
- A role blueprint withholds publishing or deletion from agents with the plugin permissions `agentsPublish` and `agentsDelete`, even where the role may publish or delete in the Panel. The cap applies to existing connections on their next request.
- "Agents prepare, editors publish" stays the default and the pitch. A connection that publishes or deletes was given that power on purpose, and publishing still fails on the blueprint's validation errors.
